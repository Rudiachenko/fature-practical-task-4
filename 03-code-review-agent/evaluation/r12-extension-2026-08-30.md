## 4. Scoring method — adaptation for n=6 per model, disclosed explicitly

`context/TICKET.md`'s own rule ("fail = a new false claim not present in the model's *other* run") was
written for exactly n=2. With 4 additional runs per model (6 total, though the 4 new ones here are a
*separate, unpooled series* of their own), "the model's other run" is ambiguous. **Adaptation used for
this document**: each of the 12 new runs is scored **independently** — `PASS` = zero verified-false claims
in that run; `FAIL` = one or more verified-false claims in that run, quoted and justified individually.
This subsumes the original rule (a claim that is false in one run and does not recur in "the other run" is
certainly "new" under the n=2 rule too) without requiring an arbitrary choice of which of 4 runs counts as
"the other one." **Raw per-run counts are reported below** so a reader can independently apply a stricter
or looser rule.

Every claim was checked against `evaluation/ground-truth-fileutils.md` and the real fixture content,
using the same trap list as the original scoring (magic-number claims not tracing to line 18's literal
`1`; resource-leak/unclosed-stream claims; "cause not chained" claims about lines 48-49; "deep nesting"
overstatement claims; "unused import" claims; "no comments at all" claims; generic field/equals/hashCode
critiques on a class with zero instance fields). Consistent with the original scoring's own precedent
(`gpt-4o` run 1's "two minor off-by-one citations, substance still accurate" was **not** counted as false),
a citation that is off by one line but whose described content/behavior is accurate for an adjacent line
is **not** counted as a fail-triggering false claim here either — only claims that misdescribe what the
code actually does, or assert something contradicted by the file, are scored `FAIL`.

### The two verified-false claims, quoted verbatim

**1. `gpt-4o` run 4 — Common Anti-Patterns section:**

> "The normalization of the `path` (lines 16–19) appears robust, but string manipulation via
> `substring(1)` can lead to `StringIndexOutOfBoundsException` if the method were executed under an
> unusual environment or corrupted input that may bypass validation."

**False, verified against the file.** `substring(1)` (line 18) is only ever reached inside the
`if (trimmed.startsWith("/"))` block (line 17) — structurally, the guard cannot be "bypassed" while still
reaching line 18, since line 18 is nested directly inside it. `startsWith("/")` returning `true` already
guarantees `trimmed.length() >= 1`, and `String.substring(1)` is valid (returns `""` at worst) whenever
`length() >= 1`. There is no code path, corrupted input or not, on which line 18 throws
`StringIndexOutOfBoundsException`. This is scored `FAIL`-triggering rather than a merely generic/hedged
opinion because it makes a specific, checkable technical assertion about specific cited lines that is
contradicted by the file's actual control flow — not a stylistic preference.

**2. `gpt-4.1-nano-2025-04-14` run 5 — Code Quality → Readability section:**

> "- **Readability:**
>   - Clear and straightforward code.
>   - Comments explain key steps, e.g., handling of the leading slash and candidate paths.
>   - Use of constants instead of hardcoded strings (e.g., `"src/main/java"`)."

**False, verified against the file.** The fixture declares zero constants anywhere (no `static final`
field, no named constant of any kind — `"src/main/java"`/`"src/test/java"` are raw inline string literals
at lines 27-28). Read literally, this bullet asserts the code *currently* uses constants instead of
hardcoded strings, which is the opposite of the file's actual content. **This claim is also
self-contradicted within the very same response** — its own later "Suggestions" section says "Extract
magic strings/constants into well-named `private static final` fields," which only makes sense if no such
constants exist yet. **Disclosed nuance**: this reads most naturally as a positive/descriptive bullet
given its placement and lack of a "consider"/"should" qualifier, but the phrasing is genuinely a little
ambiguous (it could theoretically be a garbled recommendation). It is scored `FAIL` here because, taken at
face value against the actual file, it is a specific, checkable claim about the code's current state that
is false — but a reader who judges this a formatting artifact rather than a substantive claim would
reasonably score this run `PASS`. That ambiguity, and this exact reasoning, is disclosed rather than
silently resolved either way.

### Flagged generic/templated claim (not counted toward a `FAIL`, per the original scoring's own precedent)

## 8. Updated recommendation, stated narrowly

This supplementary evidence does not overturn the formal 2-run headline result (still the ticket's own

- **`gpt-5-mini-2025-08-07` remains the strongest, most consistent reviewer measured across all 18 runs

  other.
- **`gpt-4.1-nano-2025-04-14`'s original "zero false claims across both runs" no longer holds once 4 more
  runs are measured** — 1 of its 4 new runs has a verified (if disclosed-as-debatable) false claim. It is
  no longer accurate to describe this deployment as flawless; it is accurate to describe it as
  *comparably* reliable to `gpt-4o` in this series, both clearly behind `gpt-5-mini`.
- **Sample-size caveat, restated and still binding**: 18 runs total across two non-pooled series on one
  53-line file remains a small, single-file sample. This document's own internal comparisons (12 runs,

## 9. Reproducibility lesson (see also `context/PROGRESS.md`)

The original 6-run series saved only request *shape* (`requestParametersUsed`'s three booleans), never
the literal `messages` array actually sent. That is a genuine reproducibility defect: it made this
extension's step 1 (byte-identical replication) impossible, and the token-count-based identity check in
step 1 above is the closest achievable substitute, not an equivalent. **All 12 new run artifacts in this
series fix this going forward**: every one of them carries the full literal request body in its own
`requestBody` field. **Any future run of this or a similar harness must persist the full request body
verbatim, not just parameter-presence flags**, or this same gap recurs.
